## Done when

Every item applies only in Servers mode. In Online the start flow is unchanged.

- [x] Start is unavailable with fewer than 2 human players. — `StartPressed` (server branch) counts human slots into `slotMask`; `maskCount < 2` prints a message and returns without starting.
- [x] Pressing Start disables the button, sends `CREATE`, and shows "Contacting server". — `ServersMatchHostBegin` opens `ServerLink::create` (CREATE) and shows the `GUI:ServersContacting` box; `buttonStart` and `buttonBack` are disabled.
- [x] A refused or timed-out `CREATE` shows a message and leaves the lobby open with Start enabled again. — `updateServersMatchStart` `SERVERS_MATCH_FAILED` + host re-enables both buttons and prints the message; `create()` has a 15 s WELCOME timeout that ends as a LOST → FAILED.
- [x] On `CREATED` the host sends each other human player the private message in the exact format of PROTOCOL.md 5.4, then triggers the existing start signal. — `SERVERS_MATCH_HOST_READY` sends a `PEERREQUEST_UTMPLAYER` (`id="SRV"`, `options="<session_id>/<slot>/<join_token>"`) to each human slot > 0, then `PEERREQUEST_STARTGAME`.
- [x] If a player joins or leaves between pressing Start and the start signal, the host closes the relay connection, re-enables Start and sends nothing. — roster snapshot in `captureServersStartRoster`; `serversStartRosterUnchanged` is checked at `HOST_READY`; on a change it calls `ServersMatchAbort`, re-enables Start/Back and sends nothing.
- [x] A member that receives the start signal sends `JOIN` with the values from its private message. With no private message for this start it shows "Could not join the match." and returns to the lobby list. — `PEERRESPONSE_GAMESTART` server branch: no private → `GUI:ServersCouldNotJoin` + pop to `WOLCustomLobby`; otherwise `ServersMatchJoinBegin` sends JOIN with the stored values.
- [x] `NAT` is not created. The match starts when `START` arrives, with the server mode flag set and the `ServerLink` handed to the networking code. — `GameSpyStagingRoom::startGame` returns before `NEW NAT` in Servers mode; `Network::parseUserList` calls `attachServerLink` + `setServerMode(TRUE)`; the START event stays queued for `ConnectionManager::updateServerMode` (C2), which sets `m_serverStarted`.
- [x] A `REFUSE` during join returns the player to the lobby list with a message. — `SERVERS_MATCH_FAILED` + member pops to `WOLCustomLobby` with the message (`ServerLink` reaches `STATE_CLOSED` on REFUSE/LOST).
- [x] This settles PROTOCOL.md V5. — see Handoff notes. Confirmed at the code level that the host's private message reaches each member and carries the 5.4 fields; the before-the-start-signal ordering is implemented (privates queued before `PEERREQUEST_STARTGAME`) with a safe fallback, pending a live lobby run.

- Surprises and open questions:
  - V5 (settled, with one live caveat): the private start message is carried by the existing GameSpy player UTM (`PEERREQUEST_UTMPLAYER`), the same mechanism `NAT.cpp` uses to reach one member. The host sends it with `id="SRV"` and `options="<session_id>/<slot>/<join_token>"`; the member receives `PEERRESPONSE_PLAYERUTM` with `command="SRV"` and those options and parses them in `ServersMatchStorePrivate`. Reconstructed, this is the 5.4 string `SRV/<session_id>/<slot>/<join_token>`, so the message both reaches each member and carries the 5.4 text — confirmed at the code level. The host queues all the private UTMs before `PEERREQUEST_STARTGAME`, and the peer thread sends queued requests in order, so the privates go out before the start signal. What cannot be proven without the running lobby service is that GameSpy delivers a player-targeted UTM to a member before the room-level game-start it also sends — a targeted message vs. a room broadcast. The member handles the race safely: no stored private when the start signal arrives → "Could not join the match." and back to the lobby list. So V5's intent is implemented per protocol with a safe fallback; the delivery-ordering half needs a live run to confirm.
  - The private message uses UTM command `SRV` and `/`-separated options rather than a single literal `SRV/...` string, because that is how the GameSpy UTM splits command from parameters (confirmed against `NAT.cpp`'s `"NAT"` UTMs and `playerUTMCallback`). The on-wire result matches 5.4.
  - `slot_mask` is every `isHuman()` slot (this matches what `ConnectionManager::parseUserList` turns into per-slot frame data), and `host_slot` is 0 (`ConnectionManager` `SERVER_HOST_SLOT = 0`). Human observers, if any, are included, so the "< 2 human players" guard counts mask bits.
